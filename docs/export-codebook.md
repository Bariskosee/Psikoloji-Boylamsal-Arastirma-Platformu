# Export Codebook

Normative definition of exported data structure and, above all, of **missingness**. Implements **FR-32**, **FR-34**, **FR-35**, **FR-36**, **FR-43**.

A CSV generated by this platform is also generated with a machine-readable `codebook.csv` describing itself. This document specifies both.

---

## 1. Why this document exists

The most damaging failure this platform can produce is not a crash. It is exporting a missing value as `0`, having it averaged into a mean, and having that mean published.

A blank cell in a longitudinal dataset can mean at least six different things, and they are not statistically interchangeable:

- the participant had not reached that point in the protocol yet;
- the window was open and they were still working on it;
- the window closed without them ever opening it;
- they opened it, answered other items, and left this one blank;
- the item was optional and they deliberately skipped it;
- they had withdrawn before that point.

"Missed the whole session" and "skipped one optional item" call for entirely different handling in any missing-data analysis. The export must therefore never force the analyst to guess.

**The rule:** the `value` column carries data only when `response_status = ANSWERED`. In every other case `value` is empty and `response_status` carries the reason.

---

## 2. The missingness contract

Exactly one status applies to every (participant, protocol step, occurrence, question) cell.

| `response_status` | Session state | `value` | Meaning for analysis |
|---|---|---|---|
| `ANSWERED` | `COMPLETED` | the value | Real data |
| `SKIPPED_OPTIONAL` | `COMPLETED` | *(empty)* | Deliberate non-response to an optional item |
| `MISSED_ITEM_PARTIAL` | `EXPIRED_PARTIAL` | *(empty)* | Engaged with the session but never reached or answered this item |
| `MISSED_SESSION` | `EXPIRED_UNSTARTED` | *(empty)* | Never opened the session at all |
| `IN_PROGRESS` | `AVAILABLE`, `STARTED` | *(empty)* | Window open at export time; not yet missing |
| `NOT_YET_DUE` | `PENDING_TRIGGER`, `SCHEDULED` | *(empty)* | Protocol had not reached this point |
| `NOT_APPLICABLE` | `CANCELLED` | *(empty)* | Withdrawn or otherwise cancelled |

**Prohibited representations.** No export path may ever emit: `0` for a missing value · `NA`, `N/A`, `null`, `NULL`, `-99`, `999` or any other sentinel inside `value` · a whitespace string that could be confused with a genuine short-text answer.

An empty `value` combined with `response_status = ANSWERED` is a bug and must fail export validation. (An intentionally blank short-text answer is `SKIPPED_OPTIONAL`, not `ANSWERED`.)

## 3. Long format — `long.csv`

One row per (participant, protocol step, occurrence, question). This is the primary format for repeated-measures analysis.

| Column | Type | Notes |
|---|---|---|
| `participant_public_code` | text | e.g. `P-A82F91`. The only participant identifier present. |
| `study_id` | uuid | |
| `protocol_version` | integer | Version bound at enrollment (NFR-17) |
| `step_key` | text | Stable step identifier, e.g. `daily` |
| `step_index` | integer | Order within the protocol |
| `occurrence_index` | integer | 0-based; always 0 for non-recurring steps (FR-38) |
| `participant_session_id` | uuid | Join key back to the platform |
| `session_status` | enum | The FR-14 state |
| `questionnaire_key` | text | |
| `questionnaire_version` | integer | |
| `question_key` | text | **Stable across versions** (FR-43). Use this for longitudinal joins. |
| `question_version_id` | uuid | Identifies the exact wording shown |
| `question_type` | enum | `likert`, `single_choice`, `multiple_choice`, `numeric`, `short_text` |
| `question_text` | text | As shown to this participant, in the locale they saw |
| `response_status` | enum | **§2 — read this before reading `value`** |
| `value` | text | Empty unless `ANSWERED` |
| `value_label` | text | Human-readable option label where applicable |
| `answered_at` | timestamptz | UTC |
| `scheduled_at` | timestamptz | UTC |
| `available_from` | timestamptz | UTC |
| `available_until` | timestamptz | UTC |
| `completed_at` | timestamptz | UTC, empty unless completed |
| `participant_timezone` | text | IANA, for converting the UTC columns to local time |

**Value encoding by question type**

| Type | `value` | `value_label` |
|---|---|---|
| `likert` | The numeric code of the chosen option | The anchor label, e.g. `Strongly agree` |
| `single_choice` | `option_key` | The option label |
| `multiple_choice` | Selected `option_key`s joined by `;` | Labels joined by `;` |
| `numeric` | The number as entered | *(empty)* |
| `short_text` | The text, CSV-quoted | *(empty)* |

Multiple-choice uses a semicolon rather than a comma to avoid ambiguity inside CSV, and the codebook lists every option so the field can be split reliably.

## 4. Wide format — `wide.csv`

One row per participant. Columns are generated as:

```text
{step_key}_{occurrence_index}__{question_key}
```

Example: `daily_3__mood_1`, `baseline_0__age`.

Alongside each value column, a status column is emitted:

```text
{step_key}_{occurrence_index}__{question_key}__status
```

This doubles the column count and is deliberate. A wide file without status columns forces the analyst back to §2's ambiguity, which defeats the purpose.

Leading columns: `participant_public_code`, `enrolled_at`, `participant_status`, `elapsed_compliance`, `strict_compliance`, `participant_timezone`.

**Stability guarantee.** Column names depend on `step_key`, `occurrence_index`, and `question_key` — all stable across versions (FR-43). Publishing a new questionnaire version that rewords a question does **not** change any column name. Adding a question adds a column; removing one leaves the historical column populated for participants who saw it and `NOT_APPLICABLE` for those who did not.

**One instrument, two administrations.** When a protocol administers the same questionnaire version at two steps — the pre/post shape of the reference design (FR-47) — the two appear as separate column groups distinguished by `step_key`, carrying **identical `question_key` suffixes**:

```text
baseline_0__mood_1   baseline_0__mood_1__status   …
endline_0__mood_1    endline_0__mood_1__status    …
```

That is the intended layout: a pre/post comparison is then a direct column pair, with no key reconciliation. Which column groups are the same instrument is stated explicitly in the steps section of the codebook (§5) rather than left to be inferred from naming.

**Column count.** The reference design produces 500 column groups — 100 baseline, 300 daily (30 occurrences × 10 items), 100 endline — and roughly 1 000 columns once status columns are paired in. This is well inside spreadsheet limits, but wide format degrades as a working format long before it becomes invalid: long format remains authoritative and is the format to reach for with a long recurring block.

**Known limitation.** Wide format is well-defined only when `question_key` values are unique and stable. If a study reuses a key for a semantically different question, the wide file silently merges them. The platform prevents this by prohibiting key changes after data collection (FR-43), but a study that was misconfigured before its first response can still produce this. Long format is always authoritative.

## 5. Codebook — `codebook.csv`

Emitted with every export so the dataset is self-describing and reproducible without access to the platform.

| Column | Notes |
|---|---|
| `question_key` | |
| `question_version_id` | One row per version actually used in this export |
| `questionnaire_key`, `questionnaire_version` | |
| `question_text_en`, `question_text_tr` | Both locales where configured |
| `question_type` | |
| `is_required` | |
| `option_key`, `option_label_en`, `option_label_tr`, `option_value` | One row per option |
| `numeric_min`, `numeric_max` | For numeric items |
| `first_seen_at`, `last_seen_at` | Bounds the version's use |

The codebook also includes a fixed trailer section listing all seven `response_status` values with the definitions from §2, so an analyst who receives only the CSV files can interpret missingness correctly.

### Steps section — `steps.csv`

Emitted alongside the codebook. One row per protocol step in the exported protocol version, so the design is reconstructible from the files alone.

| Column | Notes |
|---|---|
| `step_key`, `step_index` | The wide-format column prefix and the protocol order |
| `questionnaire_key`, `questionnaire_version` | **The instrument administered at this step** |
| `occurrence_count` | 1 for a single measurement; 30 for the reference design's daily block |
| `trigger_description` | Human-readable, e.g. `enrollment + PT0S` or `fixed start + P30D` |
| `window_duration_iso` | |
| `counts_toward_compliance` | So a reader can reproduce the denominator in §3 of `docs/compliance-formula.md` |
| `repeats_step_key` | Empty, or the earlier `step_key` administering the same `questionnaire_version_id` |

`repeats_step_key` is what makes a pre/post design **machine-readable**: an analyst's script reads `endline` → `repeats_step_key = baseline` and pairs the two column groups without anyone hard-coding step names or trusting that two similarly-named columns measure the same thing. Without it, "are `baseline_0__mood_1` and `endline_0__mood_1` the same item?" is answerable only by asking the research team, and the CSV set stops being self-describing (FR-47).

## 6. Export integrity rules

1. Exports contain `public_code` only. **No email, no phone, no push endpoint, no continuity credential, no IP address.** This is enforced by the database role used by the export code path, not by convention (NFR-03).
2. Every export writes an audit event recording the actor, study, format, scope, row count, and timestamp (NFR-05).
3. All timestamps are UTC, ISO 8601, with an explicit offset. `participant_timezone` is provided for local conversion.
4. Files are UTF-8 with a BOM, so that Turkish characters open correctly in Excel without manual import settings.
5. Line endings are CRLF for Excel compatibility; quoting follows RFC 4180.
6. A study with zero responses exports headers and zero data rows — never an empty file, never an error.

---

## 7. Required tests

- every one of the seven `response_status` values is produced by a fixture designed to trigger it;
- `value` is empty for all six non-`ANSWERED` statuses, verified cell by cell;
- no export cell anywhere equals `0` where the underlying response is absent;
- long-format output reconciles row-for-row against the `responses` table for a fixture study;
- wide-format column names are unchanged after publishing a questionnaire version that rewords a question;
- a recurring step with 7 occurrences produces 7 distinct occurrence indices in long format and 7 column groups in wide format;
- a 30-occurrence block exports all 30 occurrence indices, with `NOT_APPLICABLE` for any cancelled by late enrollment;
- two steps administering the same questionnaire version produce two distinct column groups whose `question_key` suffixes are identical, and `steps.csv` records the second step's `repeats_step_key`;
- multiple-choice values round-trip through the `;` separator;
- the codebook lists every question version referenced by the long file;
- an export attempted by a `VIEWER` is rejected and audited;
- an export query that joins identity data fails at the database.
